🖥️ Hardware

  • The physical, tangible parts of a computer
  • CPU — the "brain"; fetches and executes instructions
  • RAM (Memory) — fast, temporary workspace
  • Storage (SSD/HDD) — permanent storage for files
  • I/O devices — keyboard, mouse, monitor, printer

💻 Software

  • The instructions hardware follows
  • System software — manages hardware & resources (the OS, drivers, utilities)
  • Application software — helps users do tasks (browsers, games, the C++ programs you'll write)
  • Without software, hardware just sits idle
⚠️ Common Misconception

"RAM and storage (SSD/HDD) are basically the same thing." They're not. RAM is fast and volatile — it holds whatever the CPU is actively using right now, and it empties out when the power is off. Storage is slower but non-volatile — it keeps your files and programs permanently, even after a shutdown. A computer needs both: RAM for speed while it's running, storage for keeping things afterward.

The Fetch – Decode – Execute Cycle

  • Fetch — the CPU retrieves the next instruction from memory
  • Decode — the CPU translates the instruction into a signal it can act on
  • Execute — the CPU carries out the instruction (calculate, move, compare)
  • This cycle repeats — billions of times per second

Where Data Lives While It Works

TierSpeedCapacityHolds
CPU RegistersFastestTiniestData being used right now
RAM (Memory)FastLargerRunning programs & active data
Storage (SSD/HDD)SlowerLargestData permanently, even powered off

Speed decreases and capacity increases as you move down the hierarchy.

A computer does nothing until a human tells it what to do, step by step. We program to automate tedious tasks, solve problems at scale, build the tools we use every day, and model real-world systems.

Three Levels of Programming Languages

LevelWhat It Looks LikeTrade-off

Assembly LanguageShort mnemonics (MOV, ADD, JMP)Closer to hardware, still tied to one CPU type
High-Level LanguageEnglish-like syntax — C++, Python, JavaReadable & portable, but needs a compiler/interpreter

Syntax vs. Semantics

Syntax — the rules that define valid statements (like grammar). Semantics — the meaning behind those statements (what they actually do).

Why C++?

Combines high-level readability with low-level control. Used in games, operating systems, embedded devices, and finance — and gives you a strong foundation for learning object-oriented design.

Every program can be broken into three stages: Input (data the program receives), Process (instructions that transform the data), and Output (the result the program produces).

🧩 Worked Example — Rectangle Area Program

Here's the reasoning a programmer walks through to map a task onto the IPO model:

AskWhat data does the program need before it can do anything? → The user's length and width.
InputThose two values are gathered from the user. In C++, that's the job of cin.
AskWhat needs to happen to that data to get a useful result? → Multiply length × width.
ProcessThe multiplication is the transformation step — handled by an expression like area = length * width;
AskWhat does the program need to show the user? → The calculated area.
OutputThe result is displayed back to the user. In C++, that's the job of cout.

  • Analyze — understand the problem & requirements
  • Design — plan the algorithm or logic
  • Code — write the source code
  • Compile — translate code into machine instructions
  • Test & Debug — run it, find issues, and fix them
  • Maintain — update and improve it over time

This is a cycle, not strictly linear — testing often sends you back to design or code.

⚠️ Common Misconception

"If my program compiles successfully, it's finished and bug-free." Not true. Compiling only translates your code and catches syntax errors — typos in the language's grammar. It cannot catch logic errors, like a formula that runs fine but produces the wrong answer. Logic errors are only caught by testing (comparing actual output to expected output) and fixed by debugging.

Procedural Programming

  • Code is a sequence of steps, grouped into functions
  • Data and functions are kept separate
  • Runs top to bottom with loops & branches
  • Works well for small, straightforward tasks

Where It Struggles

  • Large programs get hard to organize & maintain
  • Data can change unexpectedly from many places
  • Real-world "things" (a Car, a Student) are hard to model directly
  • Code reuse across projects is limited
AspectProceduralObject-Oriented
FocusFunctions & step-by-step logicObjects that combine data and behavior
Data handlingSeparate from functionsBundled with related behavior
Real-world modelingWeaker fitStrong, natural fit
Code reuseLimitedHigh — via classes & inheritance
⚠️ Common Misconception

"OOP is just procedural programming with fancier syntax." It's more than syntax — it's a different way of organizing a program. OOP bundles data and the behavior that acts on it into a single unit (an object), so a Car object owns its own speed and its own accelerate() behavior together. That bundling is what enables better modeling, reuse, and maintainability — not just a new way to write the same structure.

🌍 Real-World Case Study — Library Management System

Imagine you're asked to build software for your campus library to track books and members. A procedural approach might use separate arrays for book titles, due dates, and borrower names, with standalone functions like checkOutBook() that reach into all of them — data and logic scattered and easy to desynchronize.

An object-oriented approach instead creates a Book object (with its own title, due date, and isOverdue() behavior) and a Member object (with their own name and borrowed-books list). Each object manages its own data — which is exactly the kind of real-world modeling OOP is built for.

Your turn (design/create): sketch two more classes this Library System would probably need. For each, name one property (data) and one behavior (action) it would have.

Librarian — property: employeeId; behavior: issueFine().
Catalog — property: bookList; behavior: search(title).
Many valid answers exist — the key is that each class bundles its own data with its own relevant actions.
